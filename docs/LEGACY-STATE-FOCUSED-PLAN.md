# RWKV State Recall：立项评估与实施方案

> 历史方案。当前的四因子政策与模型自评见 [RWKV Priority Memory](PLAN.md)。

调研日期：2026-11-18。对象：冻结权重的 RWKV-7 x070、本地对话服务、单机单用户优先。下文的阈值是拟定验收线，不是实测成绩。本项目与 RWKV 官方无隶属关系。

## 当前设计决定：先排「值得留下谁」，再看「能否答对」

保存优先级是主目标。对于一条可辨认的记忆，在其他条件相同时，**越重要、伴随的情绪越强烈（不论正负）、同一内容被独立提及的次数越多、时间越近，保存优先级就越高**。这四项从第一版起都参与排序，不是必须四项同时满足，也未规定哪项一律压倒另一项。权重、频次的去重方式和新近性的时间口径不是已定结论。建议将事件发生时间与最近一次真实提及时间分开记录，不用系统自己复述或检索来刷高频次。

排序在没有查询时也成立：工作记忆容量有限，就优先保留排前的内容；经授权的原文仍可全量归档，低分不等于删原文。第一项验收是相同容量下留下了哪些记忆：只改变四个因素中的一个，其余不变，检查对应记忆的优先分与两条记忆的相对顺序。RWKV 的衰减调制是落实此策略的一个手段；RAG 和问答召回率不是保存排序本身。

以下保留此前的技术调研和已运行的探针。凡写到“首版只做两因子、情绪权重为零、召回提升是首要门槛”的地方均属旧实验设定，不是当前产品目标。当时的代码和配置尚未实现四因子排序。

## 1. 旧版技术评估：独立实验与内核 PR

**值得立项，但要分别押注。** 原文可追溯、能删除、能检索，是一条有独立用途的工程线；改变 state 的衰减是否让模型隔很久还能答对，是另一条可能失败的研究线。值得验证的不是“能不能改门控”，而是“关掉检索以后，改动是否还带来可重复、代价可接受的记忆收益”。

| 原构想 | 核验与取舍 |
|---|---|
| 多因子选择性保留重要事实 | 原生 RWKV-7 已有依输入变化的门控和广义 delta rule；不是把固定衰减换成动态衰减。额外贡献应表述为**外部重要性信号能否改善原生更新**。[1][2] |
| 分数高就锁住对应记忆 | 一个 token 分数不含该事实在各层、头或矩阵列中的地址。矩阵列上叠加了许多历史信息；多保留一列也会保留无关或过期信息。首版只声称“短时改变旧状态的保留程度”。[2] |
| 不改权重、不改前向、零延迟 | 可以不重训基座；启用调度必然改变前向数值。固定模型尺寸时开销可以不随历史长度增长，但打分、逐元素运算、设备同步都有成本。默认 off 要直接走原路径，性能另测。 |
| 全量备份就没有决策风险 | 已存原文、可被检索、被正确注入、模型据此答对是四件事。默认不落盘；开启后在授权范围内不按重要性筛原文。用户撤销、敏感内容和删除优先于“全量”。 |
| 首版合并调度、情感、三种向量后端 | 拆成独立可关闭的调度、归档、检索。先做两因子与本地基线，MLP、情感、Qdrant/Milvus、融合内核都不是 MVP 的依赖。 |

**已有相邻工作。** Generative Agents 将近期性、重要性、相关性用于记忆条目检索。[13] MemoryBank 用遗忘曲线、时间和重要性更新外部记忆。[5] 因此不应把“多因子仿生记忆”作为原创主张。

RWKV-7 State Tuning 研究优化初始状态等途径。[6] EmbeddingRWKV 对模型微调以复用文档 state 做检索/精排。[14] 两者都不等同于在冻结模型的逐步衰减上叠加有界控制。

上游有 RWKV-8/ROSA 的独立实验。[12] 本项目不承诺兼容 ROSA，也不依赖 RPU 或任何硬件路线。本次检索不是穷尽性查新，不主张“首次”。

## 2. 模块 A：限定版本的 state 调度

**挂载点已查实。** 固定 `BlinkDL/RWKV-LM@2eebb381a6160837ac45896c60d6963ef3cda929`。先用 `RWKV-v7/rwkv_v7_demo_rnn.py` 的 `RWKV_RNN.forward` → `time_mixing__`（112–150 行）；只动每层的 WKV 矩阵 `state[i*3+1]` 的更新，不改另外两个 Token Shift 向量、权重或 tokenizer。[2]

`rwkv_v7_demo_fast.py` 分 `RWKV_x070_TMix_one` 和 `RWKV_x070_TMix_seq`；后者把编码后的衰减传入 `RWKV7_OP`，CUDA 示例明确只支持 B=1。[3][4]

固定版本的 Albatross 有多种实现与状态布局，递归文件树中没有原稿假定的 `albatross/state_manager.py`；不能把这个路径当作公共接口。[11][15]

**按参考代码（每头、列向量约定）：** `S_t = S_prev @ diag(w) + S_prev @ [(-kk) (kk⊙a)^T] + v k^T`。`kk` 是上游归一化后的 key，最后一项的 `k` 是上游调制后的 key，不要混用。`w` 是实际保留系数，越接近 1 衰减越慢；它只乘旧状态。由此可知 `S_prev=0` 时，仅改变此步 `w` 不会加深本次写入。原文的 `η` 不能当作现成独立标量旋钮；改变 `a` 又会改变校正项。[1][2]

**首个候选：只影响未来的保护痕迹。** 明确拆开“这次信息重要”和“它在随后的 token 还需要保留多久”。以下是新设计而非论文公式；标量原型在 `spikes/decay.py`。

```text
u_t ∈ [0,1]        当前可见输入产生的重要性信号；明确“请记住/更新为”的事实片段取高值
p_0 = 0            每个会话单独初始化；以下 p_prev 是本 token 之前的状态
q_t = exp(-λ · M · p_prev)
w_eff = w ^ q_t    仅对保留乘子操作；在矩阵更新中替换 w，其他两项不动
p_next = max(u_t, 2^(-1/H) · p_prev)     # 本步结束后更新，供下一 token 用
```

起点 `λ=0.10`、半衰期 `H=64 token`、掩码 `M=1`，是待检验的可复现配置。默认 `off` 或 `λ=0` 不调用控制器。首版标量广播到各头，不宣称找到了某条事实的通道；低分仅让保护自然结束，回到原生衰减。若要加速遗忘旧信息，列为单独、有上下界的对照，不能同时改写入制造假收益。例：当原始 `w=0.8`、`p_prev=M=1` 时，有效值约 `0.81717`。若再无增强，1024 个 token 后痕迹仅约 `0.0000153`；长距离增益不能由这个公式直接推出。

**打分边界。** 首版事先冻结中英文前缀规则或采用用户显式标记；所有实验臂看到相同文字。交互式输入仅用已读前缀；只有收到完整用户消息才可做整轮打分，并须另标为轮级模式。系统提示、检索引用、模型自己生成的“记住”不能给自己提权。时间先用 token 距离而非墙钟（可离线重放）。后续候选：在开发集冻结层/头掩码与随机同规模掩码比较；或以当前归一化 key 作为软掩码，称为启发式定位，不称为地址。新增 density 可用长度归一化的新实体/去重词比例；emotion 默认权重为零，强烈抱怨未必比平淡的地址变更重要。只在独立数据上观察增益后才启用。若用 MLP，需单独标注重要性/未来引用数据、拆分训练与验证会话、冻结基座、训练/校准头并测耗时；随机头没有语义保证。金标答案、未来提问和检索返回不得输入打分头。

**快速路径不能复用裸 `w`。** 逐 token 参考函数已算出 `exp(-0.606531*sigmoid(...))`；序列内核收到的是 `z`，在内核内计算 `exp(-exp(z))`。若要实现同一个幂调制，对编码量应传 `z_eff=z+log(q_t)`，不是向内核传 `w_eff`。先做慢参考，再验分块 prefill 与逐 token decode 接续的 state/logits；首版不改 CUDA。启用但后端不支持，须明确报错或经用户选择回退参考实现，不能静默声称已启用。[2][3][4]

**写入是第二个独立假设。** 研究版可以引入 `g_write·v k^T`（恒等值 1、范围预注册），先测 write-only，再测与 decay 的交互，并监控状态范数、NaN、语言质量。只改外积，不无意缩放同一 `v` 在其它旁路中的使用。[2] 无独立收益就删除该实验。状态与痕迹按 `(主体, 会话, 分支, 模型/词表/策略版本)` 绑定，换版本或撤销时不得继续复用旧缓存。

## 3. 模块 B/C：原文档案、索引、按需读取

```text
授权的真实消息 → 原文事件 + outbox（同一个 SQLite 事务）→ ack: archived
                         ↓ 可重试的后台 worker
                 分块/嵌入 → 本地词法/向量索引 → ack: indexed
问句 → 权限/时间/删除范围 → 候选检索 → 去重排序 → 限长引用 → 临时回答分支
正常对话 token → 原生 RWKV 或受控 state；无检索时不访问索引
```

**写入协议。** `archive.append(event, consent) -> archived | skipped | failed`。事件键为 `(user_scope, session_id, turn_id, role, revision)`；存原始 UTF-8 文本（不要只用解码重构用户原文）、可选 token IDs、模型/词表指纹、UTC 时间、来源、授权/保留策略、`supersedes_id`；打分连同策略版本可空。原文、幂等键、任务同事务落地后才回“已保存”。同键同内容可重放，同键不同内容拒绝或新建版本。`WAL + synchronous=FULL` 是本地候选，SQLite 文档区分 FULL 的逐提交同步与 NORMAL 的断电耐久性取舍；回合末的小额提交不等于零成本。[9]

**后台索引。** 原文库是真值，FAISS 是可重建的稠密向量检索库，不把它当事务日志。[8] 先上 SQLite FTS5 作为廉价基线；中文用合适分词或字符 n-gram 与英文分别测，现有英文短语探针不证明中文效果。第二步本地多语 embedding + FAISS CPU（归一化向量、内积）；持久化 `event_id:revision:chunk:embed_version`、模型修订和索引代次。分片快照先临时构建，验证后原子切换；跨 SQLite/FAISS 不声称 exactly-once，按至少一次投递、可幂等重建设计。重启领回超时任务、指数退避/死信、积压监控；写入速度超过消费时延后向量化，不悄悄丢原文。磁盘满则记失败、告知“本轮未存”，可允许继续对话。索引落后时允许在授权范围内对最近原文做补查。需要容量或多客户端时才评估 Qdrant；Milvus 是更大规模备选，不是三个后端同时开发。单算 10 万条 384 维 float32 裸向量约 146.5 MiB，尚不含文本、索引和备份；按实际摄入量设置配额和磁盘告警。

**读取协议。** `retrieve(query, allowed_scope, as_of, k, budget) -> evidence[]`。默认当前用户、当前会话；跨会话必须另授权。先分用户/可见集合取候选，再复核归档权限、删除标记、有效时间及更新关系；不能全库取 top-k 后才靠 prompt 隔离。词法命中适合编号，向量补同义改写；推荐先各取候选、用排名融合 RRF，再按事实时间/修订轻量重排。携带来源回合、时间、片段偏移；按有效版本回答“现在”，按 `as_of` 回答“当时”。无证据则承认不知道。首测两条检索臂每题都查，之后才比较显式“之前说过”、时间词、标识符规则与 always-on 的效果/开销；token 熵只是不确定性的代理，不是 state 缺失探测器。初值 `top_k=3`、总注入上限 `256` 个 RWKV token，记录实际消耗。

**注入与删除。** 历史片段当不可信引文，不当系统/工具命令。问答时从问题前 checkpoint 建临时分支，读入引用、问句并生成；丢弃引用分支，主分支仅消费一次真实问句与可见回答。基线使用同一模板，不把已有轮次再 prefill 一次。不将引文或检索摘要当作新用户原文回写。默认不开启归档；可按会话关闭、设 TTL、脱敏/拒存凭证等内容。删除先阻断查询和在途重建，再清原文与 token IDs、FTS/向量、热缓存、旧快照；清空或从保留事件重放 RWKV state，因为无法对矩阵做逐事实擦除。WAL、备份按明确轮换期清理，不能承诺物理即时擦除。真实日志不进 Git，不去云端评测。索引服务宕掉时降级原生 state，恢复后按水位补建。

**拟建模块与开关（均不是已发布命令）。** `state_recall/scheduler.py` 只负责信号与痕迹，`adapters/x070_rnn.py` 负责后端挂载与状态生命周期，`archive.py` 和 `index_worker.py` 管落库/索引，`retrieval.py` 管权限与引文预算，`bench/` 放四臂驱动。建议独立开关 `--state-scheduler off|post-write-trace`、`--memory-store off|sqlite`、`--recall off|explicit|always`；无持久化授权时禁止跨会话检索。拆依赖：基础逻辑和 FTS 测试不导入 PyTorch/FAISS；真实后端、向量检索分别用可选依赖。

## 4. 怎样证明是调度器起作用

| 臂 | State | 查库/注入 | 回答的问题 |
|---|---|---|---|
| A | 原生 | 否 | 同一模型自己能记多少？ |
| B | 调度 | 否 | **B−A：调度有没有独立收益？** |
| C | 原生 | 是 | 只加本地检索，是否已经足够？ |
| D | 调度 | 是 | **D−C：有了同一份证据，改 state 是否仍有增益？** |

**公平性。** 固定同一权重、词表、dtype、模板、历史、生成上限（32 token）与 greedy 解码。A/B 不准读归档或提示里重放事实；C/D 对每道题使用同一组预先记录的检索片段、顺序及预算。四臂都在线消费同一历史，公开总 prefill token 数、检索成本；额外加等长无关片段对照，避免把 prompt 变长当作检索收益。每题从对应干净 checkpoint 开始，不让上一道题的答案漏给下一道。持久/跨会话测试给四臂同样的 reset 或续接规则；区分同一授权会话流长期续接与完全重置后的外部找回。以 `D−C−(B−A)` 观察交互；D 优于 A 本身不能证明调度有效。

**数据顺序。** 先用虚构事实（中英文名称、日期、编号、用户偏好），加入改口、过期版本、强情绪无关项、重要但语气平淡项、无答案题。示例：“请记住，青禾项目代号是 K47”→多轮干扰→“改为 J19”→分别问旧值、现值和未给过的负责人。问题前不重放证据。先做不计入结果的近距离/正确证据就地呈现的 oracle 检查；若读到正确证据仍答不对，换模板或更强读者，不能归咎于遗忘。

**预注册。** 试验表见 `configs/pilot.json`。主试验计划用 2 种语言 × 3 个距离（128/1024/4096 个实际词表 token）× 3 个数据种子 × 每格 10 段独立历史，合计 180 个主事实问题，四臂 720 次问答。主终点预定为较长两档共 120 问的归一化精确匹配（EM）百分点差 B−A；另报分语种、分距离。开发/确认集按会话、实体、模板隔离，额外对照题另列，不把生成种子当独立模型复现。用按会话配对、按语种和距离分层的 bootstrap 给 95% 区间，列出每格样本数。样本少或区间不确定时先报告“不足以判定”，不反复换子集找显著。扩样须冻结策略并换未看过的会话。最后用 LongMemEval v1 的固定分层子集做外部验证：它有 500 问，涉及提取、多会话推理、更新、时间和拒答；`has_answer`、`answer_session_ids` 仅用于评分；oracle 文件只测读者上限，不作普通长历史结果。公开子集 ID 与截断策略，不能冒称全量基准。[7]

**诊断。** 消融按价值排序：固定常量减慢衰减（匹配平均强度）、打乱同一数据集的重要性标记、仅时间、仅重要性、二者结合；再考虑 per-head vs 相同规模随机掩码、write-only、检索 oracle/错证据、强制 vs 按需检索、情感增量。打乱后若不变，不能把收益归给多因子。报告 `EM/F1`、更新答错旧值率、拒答准确率、证据 `Recall@k`/MRR（无证据题单列）、引文是否支持答案；bad retrieval 与 reader failure 分开。普通文本用同语料同 tokenizer 算固定 teacher-forced PPL；缓存、模型、依赖和数据版本都写 manifest。

**继续/停止条件（待测，不是承诺）。**

| 判定 | 预定条件 | 动作 |
|---|---|---|
| 读者可用 | 近距离 oracle EM ≥60%；off 与原生在相同确定性参考路径的状态及 logits 一致 | 才开始解释远距差值；不达标先修加载、词表、模板或读者能力 |
| state 值得深挖 | 主终点 B−A ≥5 个百分点，配对 95% 区间下限 >0；固定强度/打乱控制不能解释全部收益 | 在第二个权重规模和独立模板复验，才考虑后端 PR |
| 质量、性能守门 | 短文 PPL 比值 ≤1.02；同机同后端开/关时 decode 吞吐 ≥95%、p95 每 token 间隔 ≤105%；无非有限值；更新/拒答单列 | 预热、固定长度和 batch，设备同步计时，至少 5 组交替测量；同时报 prefill tok/s、首 token 时间 TTFT、峰值显存、归档提交 p95、检索 p95、积压。任一越线不默认启用 |
| 仅 RAG 有收益 | B−A 不稳定或 D−C 无可重复增益，而 C 对 A 明显有效 | 发布应用层记忆与基准；state 保留实验开关或归档，不投融合内核。若 B 有效但 D−C 不显著，定位为无检索/低时延选项 |
| 数据路径失格 | 任一越权命中、删除后仍可见、重复重试令内容复活、已确认归档却不可恢复 | 阻止发布持久化功能，不以召回率抵消数据错误 |

## 5. 本机投入、里程碑与交付边界

本机查询到两张 RTX 2080 Ti，各自 22 GiB（计算能力 7.5）；**首轮按单卡、B=1、FP16 权重 / FP32 WKV 状态设计**，不合算两卡显存，不把其它架构的吞吐当本机表现。先在独立环境验证 PyTorch 对 `sm_75` 的支持；保持模型服务不动，没有空闲卡就推迟 GPU 测试。大权重和索引放数据盘；仓库内只存代码、配置、合成样例和脱敏结果。本次未下载权重、未安装 GPU 栈、未启动常驻服务。

候选权重 `BlinkDL/rwkv-7-world` 固定修订 `2c0ebae3b3a784e690e3d46bf545ecf44deceb10`：0.4B World 文件 901,794,466 字节，LFS SHA-256 与词表指纹见配置。官方参考 demo 默认模型不是这个文件，不能照抄硬编码层数/宽度；从 checkpoint 检查模型形状、头宽、张量键和 tokenizer，先通过原生短样本测试。正式测量再用同系 1.5B 复验。有文件名 `ctx4096` 不代表超过该距离必定答对。实测输入、训练范围内外分别报告。[2][10][16]

| 阶段 | 单人估算 | 可交付物/退出条件 |
|---|---:|---|
| P0 可复现基线 | 1–2 人日 | 锁定权重、词表、模板和环境；原生输出回放；近距 oracle。先暴露模型/模板地板问题。 |
| P1 优先试错 | 3–5 人日 | 逐 token 参考适配、off 同值、A/B 先导和常量/打乱对照。若无方向，限制在一次预注册复验，不做 CUDA。 |
| P2 档案与读取基线 | 3–5 人日 | 单机归档、后台 FTS、恢复/权限/删除、引用证据、C 臂；组织为独立库，state 不通过也可交付。 |
| P3 组合对照 | 4–6 人日 | A/B/C/D 完整先导、版本化向量索引、是否真的需要按需触发；补测积压/过期事实/删除。 |
| P4 留出集与性能 | 4–6 人日 | 新模板、第二模型、外部子集；分别测 prefill/decode 和端到端。若不会改善决定，不跑大规模基准。 |
| P5 发布或收缩 | 2–4 人日 | 可复跑报告、依赖/数据许可清单、负结果；仅在过线后发讨论或最小补丁。 |

首个继续/停止判断约 **4–7 人日**，全路径约 **17–28 人日**；以一名熟悉 Python/PyTorch 的开发者、单机离线评测估算，不是交期。GPU 时数先以 10 条 pilot 记录实际耗时，再按总 token 和四臂外推；没有实测，故不承诺云预算或本机速度。建议拆分：本仓先交基准、再交检索层、最后提可选调度适配；上游只讨论最小参考 hook，不把数据库依赖塞进推理引擎。是否合并由维护者决定，英文 RFC 和当时的建仓步骤见[旧版文案](LEGACY-GITHUB-PROPOSAL.md)。

## 6. 本次实际交付与第一项正式任务

已实跑：无权重的标量公式测试；固定上游真实单层 `time_mixing__` 在合成 CPU 张量上的对照；临时 SQLite 的“已归档但未建索引→重新打开→补建→检索→删除”流程。10 个单元测试通过。**未实现或未测：真实权重整模型、语义召回增益、浮点/吞吐 GPU 等价性、独立异步服务、稠密向量检索、完整隐私擦除、LongMemEval 成绩。** 见[旧版验证记录](LEGACY-RWKV-VALIDATION.md)。

第一项正式任务不是训练分类器：在数据盘取已固定的 0.4B，验 SHA，使用原生参考适配读十条中英文虚构事实。先做有证据/无证据和 off 等价检查，再对同样的例子只开调度。若连有证据时都不能读懂，先别把结果叫作 state 遗忘。
